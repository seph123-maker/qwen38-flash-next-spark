# September 26: Blazux v0.30 source update

## Status and scope

Published source/configuration update only. The live Spark remains on Hasso/SGLang. No server was stopped, no weights changed, and no new image was built or benchmarked. `recipe-v030.json` has no claimed built-image digest. `production.json` remains the historical September 19 export.

## Inputs and changes

- Unmodified Blazux snapshot: [`5108d90`](https://github.com/blazux/qwen3.8-Flash-DGX/tree/5108d90dedf15a31aa20432319f151b2fdda17a3), in `upstream-blazux-v030/`.
- Base image: `vllm/vllm-openai:v0.30.0`, as upstream specifies. This is a release tag, not an immutable digest; record the resolved digest and built image ID when building.
- Loading patches 14–18: mmap cloning, small-tensor pread, expert-name indexing, chunked embedding copies and MTP tensor filtering. Enabled by the upstream build defaults.
- Existing PLE/hybrid/attention/parser patches use their v0.30 versions. Graph splitting operators exactly match upstream's v0.30 branch, including `ple_mmap_lookup_ids`.
- FP8 KV support is present but **not enabled**. No 1M-context qualification is claimed here.
- We retain pinned Drowzeys hybrid weights, port 8000, model name `qwen3.8-flash-next`, 500000 context, YaRN factor 4 (upstream's `YARN=1` means enabled, not factor 1), BF16 KV, utilization 0.80, eight sequences, 8192 batch tokens, PIECEWISE graphs, MTP two tokens, reduced vocabulary, prefix caching and persistent compilation caches.

## Performance evidence: upstream only

[Blazux's report](https://github.com/blazux/qwen3.8-Flash-DGX/blob/5108d90dedf15a31aa20432319f151b2fdda17a3/README.md) measures its NVIDIA checkpoint on its own box: cold prefill 1.5–2x faster than v0.29, similar decode, and boot about 3m35s after the loading patches. These are not measurements of our Drowzeys checkpoint or comparisons with Hasso.

Their corrected BF16 KV pool is roughly 520–640k tokens across bases. Earlier larger values partly reflected swap during slow loading. Our historical 710606-token reading is preserved as an observation, not a reproducible capacity guarantee. Sequential deterministic output does not imply batch invariance.

## Validation and next deployment checks

Local checks cover JSON parsing, Python syntax, generated commands for both profiles, exact graph-operator alignment, included build inputs, documentation links and publication checksums. They do not validate CUDA compilation, checkpoint loading, model output, tool parsing or memory capacity.

Before calling this a tested deployment: build on ARM64 GB10, record image digests, load the pinned hybrid checkpoint, check health and generation, run tool/parser and prefix-cache checks, and record memory/swap and representative long-context behavior. Existing benchmark files remain historical and were not rerun.

## Historical recipe

Build `upstream-blazux/Dockerfile` as `qwen38-published:20260919`, then use `python3 serve.py --profile legacy --hf-cache /path/to/cache`. Default `--profile v030` selects the new configuration and `qwen38-published:20260926-v030`. Both refuse to replace an existing named container. Neither switches another serving service automatically.
